Local discovery that ends in a trusted interaction.

A mobile-first web app for finding nearby products and services, contacting a merchant, and leaving a rating tied to a recorded inquiry—not an anonymous profile visit.

Launch: San Jose CityPlatform: Mobile webStack: Next.js + SupabasePilot: 20 merchants
01 · Product definition

What we are building

⌖

Not another broad online marketplace

HanapDito answers: Who nearby can provide this, are they available, and how can I reach them? The MVP is a discovery-and-inquiry platform. The transaction may finish in-app, by call, SMS, Messenger, or in person.

Customer job

“I need something locally and don’t want to dig through old Facebook posts or irrelevant Google results.”

Merchant job

“I need qualified nearby inquiries without maintaining a website or repeatedly posting in groups.”

Platform job

Record the inquiry lifecycle so availability, response behavior, and ratings become more trustworthy.

02 · Core loop

The one journey MVP must complete

If this loop works with real users and merchants, the concept is validated. Everything else is secondary.

01SearchNeed + current location
02CompareDistance, availability, rating
03ViewMerchant and service details
04InquireCreate chat record
05CompleteConfirm interaction outcome
06RateVerified feedback only
External communication rule: Call, SMS, and Messenger remain available. Tapping one first creates an inquiry record and logs the chosen channel. Because the platform cannot inspect external conversations, those interactions become rating-eligible only after completion confirmation.

04 · Functional contract

Important rules before coding

AreaMVP ruleReason
BrowsingNo account required for search, results, or profiles.Reduce friction and improve discovery.
InquiryLogin required only when starting an inquiry or contacting externally.Creates a customer identity and auditable record.
ChatText-only, one conversation per inquiry. No typing indicator or presence.Enough to validate communication without cloning Messenger.
External channelCreate inquiry first, then deep-link to phone/SMS/Messenger.Preserves attribution while respecting user preference.
CompletionEither party can mark done; the other can confirm or dispute.Provides a workable rating gate.
RatingOne customer rating per eligible completed inquiry.Prevents drive-by and duplicate reviews.
SearchText + category/tag + barangay/distance + availability.Covers primary local discovery signals.
AvailabilityMerchant schedule plus manual “available today” override.Schedules alone are often inaccurate for micro-sellers.
Merchant approvalListings remain draft/pending until admin approval.Limits spam during the curated pilot.
Location privacyPublic profile shows barangay/general area; exact coordinates stay private.Protects home-based merchants.

06 · Practical architecture

Keep deployment and ownership simple

Next.jsOne application with customer, merchant, and admin route groups. Responsive only for mobile in MVP.
↓
SupabasePostgres + PostGIS, Auth, Storage, Realtime for messages, and Row Level Security.
↓
VercelPreview deployments and production hosting. Add background jobs only when notifications require them.
Turborepo decision: defer it. Begin with one Next.js repository. A monorepo adds value once there are genuinely separate deployable apps or shared packages—not during validation.
07 · Data model

Small relational core

EntityPurposeImportant fields
profilesShared user identityid, role, name, phone, avatar
merchantsPublic seller/service profileowner_id, name, bio, barangay, coordinates_private, service_radius, status
merchant_hoursSchedule and overridesmerchant_id, day, open_at, close_at, override_status
listingsProducts or servicesmerchant_id, type, title, price_from, category_id, active
listing_tagsSearch vocabularylisting_id, tag_id
inquiriesTrust and lifecycle recordcustomer_id, merchant_id, listing_id, channel, status, completed_at
messagesIn-app conversationinquiry_id, sender_id, body, read_at, created_at
ratingsVerified feedbackinquiry_id unique, score, tags, comment, moderation_status
search_eventsDemand discoveryquery, location, result_count, clicked_merchant_id

RLS principle: public users read approved merchant/listing data; customers access their own inquiries; merchants access inquiries addressed to them; only conversation participants access messages; admins moderate through explicit role checks.

08 · Build sequence

Four milestones, each independently testable

M1

Discovery foundation

Schema, seed data, location search, filters, result cards, and merchant profiles. Test using 20 real merchant records.

M2

Identity and merchant operations

Auth, roles, onboarding, profile/service editing, availability, and admin approval.

M3

Inquiry and communication

Create inquiry, Realtime text chat, external channel links, statuses, unread count, and simple report/block actions.

M4

Trust and pilot telemetry

Completion confirmation, verified rating, search event logging, basic admin reporting, polish, and private pilot.

10 · Decisions

Locked versus still open

Locked for initial direction

  • Mobile-first web app
  • San Jose City pilot
  • Discovery + inquiry, not checkout
  • In-app chat is primary
  • External contact remains allowed
  • Ratings require recorded interaction
  • Next.js + Supabase
  • One repo/app before Turborepo

Resolve before implementation

  • Product name: HanapDito, HanapSJC, or another?
  • First categories: exact 2–3 launch niches
  • Completion: one-sided timeout or strict two-sided confirmation?
  • Location: GPS, barangay selection, or both?
  • Merchant identity: personal name, business name, or either?
  • Notifications: email only or web push in MVP?
  • Moderation: who handles merchant and review disputes?
→

Recommended immediate next step

Lock the name, first two categories, and interaction-completion rule. Then create the database schema and convert the customer wireframe into a route-by-route Next.js implementation plan.
