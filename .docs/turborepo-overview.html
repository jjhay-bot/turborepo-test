One-page architecture guide

Think of Turborepo as one shelf for our school apps

We have more than one UI: a library management system for staff and a public school website for visitors. They stay separate, but can share the right foundations.

The only idea to remember

Turborepo does not build the apps. It keeps our Admin, School Portal, and future User UI in one repository, so they can share MUI building blocks and Supabase types without copying them.

Three rules

How we decide where code belongs

1

App-specific?

Keep it inside that app. Admin-only work stays in apps/admin.

2

Used by two apps?

Move it into a shared package, such as one MUI theme or common form.

3

Needs data or sign-in?

Use Supabase. Database changes are migrations; access uses RLS.

What Turbo is—and is not

No extra app to build

What it does

Keeps shared code tidy and avoids copying the same theme, types, and configuration.

What it does not do

It is not the frontend, database, authentication system, or replacement for Next.js, MUI, or Supabase.

Routes and URLs

Each app owns its own routes

Turborepo does not control browser routes. Next.js does, inside each app. The clean default is one subdomain per app.

Why subdomains?

They keep the apps independent. We can deploy and evolve the library admin, public School Portal, and future User UI separately. A single domain with /admin, /school, and /app is possible later, but needs extra routing configuration.

Simple decision: use Turborepo because we have multiple UIs. Build each UI with Next.js + MUI; use Supabase for the backend; share only code that both apps need.
