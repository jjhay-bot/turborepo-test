The one-line explanation

Turborepo keeps our Admin and School Portal together while letting them share the right code. We still build pages with Next.js, style them with MUI, and use Supabase for sign-in, database, storage, and access rules.

Turborepo 101

The four terms you actually need

Turborepo has one job: run tasks (dev, build, lint) across every app/package in the repo, in the right order, and skip work that hasn't changed. Everything else is these four ideas.

Workspace

The whole repository

One package.json at the root lists every app/package (via pnpm-workspace.yaml). Turborepo reads this to know what exists.

Task

A named script, e.g. build

Each app defines its own dev/build/lint script. Turborepo doesn't invent these—it just runs the ones already in each app's package.json.

turbo.json

The rulebook

One root file that says, for each task, what has to finish first (dependsOn) and what files/outputs to watch for caching.

Cache

Skip work that hasn't changed

If the inputs to a task are identical to a previous run, Turborepo replays the saved output instead of re-running it. This is the entire speed win.

Cheatsheet

Commands you'll actually type

Run these from the repository root—Turborepo figures out which app(s) to target.

# run every app's "dev" task at once
turbo dev

# build only the admin app (and anything it depends on)
turbo build --filter=admin

# run lint everywhere, using cache where possible
turbo lint

# force a clean re-run, ignoring cache
turbo build --force

Rule of thumb: if a task feels slow the second time you run it unchanged, something's wrong—that's the one case where Turborepo should be making things instant.

Clear boundaries

What each tool does—and does not do

Keeping responsibilities separate is what makes this stack easy to reason about.

Turborepo

Organizes the repository

Runs tasks across projects in the right order and caches unchanged work. It does not create UI, routes, or database tables.

Next.js

Builds the web application

Owns pages, routing, server-side code, and rendering. It does not replace Supabase or manage a multi-project workspace.

MUI

Creates the interface

Provides accessible components and a theme system for layouts, forms, dialogs, navigation, and data-heavy screens.

Supabase

Provides backend services

Owns authentication, database, storage, and authorization policies. It does not replace the user-facing Next.js app.

Repository map

What we will see in the project

We keep the beginning small. Shared packages only appear when another app genuinely needs the same code.

repository/
├── apps/
│   ├── admin/                # staff-facing Next.js + MUI app
│   └── school-portal/        # school-facing Next.js + MUI app
│   # later: user/             # user-facing Next.js + MUI app
├── packages/
│   ├── ui/                   # later: shared MUI theme/components
│   └── database/             # later: shared generated Supabase types
├── supabase/
│   └── migrations/           # versioned database schema changes
├── docs/                     # durable project documentation
└── .notes/                   # local plans and review explainers

Useful from day one: packages/ui can hold shared MUI foundations, while packages/database can hold Supabase types used by both apps. Feature-specific code stays inside its own app.

Day-to-day work

What development feels like

1

Build the feature in the right app

Admin-only work stays in apps/admin; School Portal work stays in apps/school-portal. Both follow the same Next.js and MUI foundations.

2

Version data changes with Supabase

When a feature needs data, create a migration in supabase/migrations and define the matching Row Level Security policy.

3

Share code only when it belongs to both apps

Put stable shared MUI foundations in packages/ui and shared Supabase types in packages/database. Keep role-specific screens and business logic in their own app.

The important part: Turborepo is valuable immediately because both apps can reuse one MUI foundation, database types, and shared configuration—without mixing Admin and School Portal feature code.
Supabase safety

Rules we will keep from day one

  • Every schema change is kept as a Supabase migration.
  • Application-facing tables use Row Level Security.
  • Public browser values use NEXT_PUBLIC_* only when safe.
  • The service-role key stays server-only and never enters Git.
  • Generated database types become shared only when multiple apps need them.
  • Reusable MUI components are promoted only after real reuse appears.
Quick decision: use Turborepo for organization, but think and build in Next.js + MUI + Supabase. The workspace grows with the product instead of forcing complexity into the first app.
